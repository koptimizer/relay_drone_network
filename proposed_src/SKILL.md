# Incremental Implementation

## Overview

조각 내어 점진적으로 코드를 구축합니다. 한 부분을 구현하고, 테스트하고, 검증한 다음 확장합니다. 전체 기능을 한 번에 구현하는 것을 피합니다. 각 증분은 시스템을 작동 가능한 테스트 가능한 상태로 유지해야 합니다.

## The Cycle

```
┌──────────────────────────────────────┐
│       구현 ──→ 실험 ──→ 검증   ──┐     │
│       ▲                        │     │
│       └───── 확인 ◄─────────────┘     │
│              │                       │
│              ▼                       │
│             다음 슬라이스              │
└──────────────────────────────────────┘
```

각 슬라이스는 다음 단계를 따릅니다:

1. **구현**: 가장 작은 전체 기능을 구현합니다.
2. **테스트**: 테스트 스위트 실행
3. **확인** : 슬라이스가 예상대로 작동하는지 확인합니다(테스트 통과, 빌드 성공, 수동 확인).
4. **커밋**: 설명 메시지와 함께 진행 상황을 판단합니다. (그 과정에서 작성된 코드는 최종에 남기진 마세요.)
5. **다음 조각으로 이동** - 앞으로 이월하거나 다시 시작하지 않습니다.

## 슬라이싱 전략

### 수직 슬라이싱

전체 파이프라인(환경 → 정책 → 평가)을 관통하는 하나의 완전한 경로를 먼저 구축한 뒤, 정책을 하나씩 추가:

슬라이스 1: 최소 실행 경로 (환경 + greedy 정책 + 평가 스텁)

→ 검증 통과. 단일 정책이 환경에서 돌아가고, 비용·서비스 레벨이 계산되어 나옴.
슬라이스 2: 두 번째 baseline 추가 ((s,S) + 폐루프 튜닝)

→ 검증 통과. (s,S)가 목표 ε에 튜닝되고, greedy와 matched-α에서 비교 가능.
슬라이스 3: SCMPC 통합 (시나리오 LP + ws 튜닝)

→ 검증 통과. SCMPC가 매주 OPTIMAL로 풀리고, 세 정책이 동일 프론티어 위에서 비교됨.
슬라이스 4: 정보 가치 분석 (VSS + θ-스윕 + H0 통제)

→ 검증 통과. VSS 계산, θ 민감도 곡선, 반증 실험까지 완료.

각 슬라이스는 "새 정책 또는 새 분석 축을 하나 추가하되, 그 시점에서 항상 실행 가능하고 검증 통과 상태를 유지"합니다.


## 구현 규칙

### Rule 0: 단순함 최우선

코드 작성 전, "가장 간단한 코드로 구현하게 할 수 있는 방법"을 고민하세요.

코드를 작성한 후에는 다음 사항들을 기준으로 검토하세요.
- 더 적은 줄로 구현할 수 있을까?
- 이러한 추상화가 복잡성을 정당화하는가?
- 가상의 미래 요구사항을 위해 구축하고 있는가, 아니면 현재 작업을 위해 구축하고 있는가?

코드가 작성된 후에는 다음 사항을 검토 해주세요.
✗ 과도한 예외처리, 과도한 안전 필터
✓ 간단한 함수, 직관적인 변수명, 명확한 로직

✗ 너무 간결함을 위해 함수 간 transition이 불분명
✓ 한 함수는 모듈 단위로 의미가 있어야 하며, transition이 명확

중복되는 코드를 최대한 제거하고, 재사용 가능한 함수로 추출하세요. 단, 추상화가 복잡성을 정당화하는지 항상 검토하세요.

### 규칙 0.5: 범위 규율 (Scope Discipline)

작업이 요구하는 것만 건드린다.

하지 말 것:
- 변경 부분 옆에 있는 코드를 "정리"하기
- 수정하지 않는 파일의 import를 리팩터링하기
- 완전히 이해하지 못한 주석을 삭제하기
- 명세에 없는데 "유용해 보인다"는 이유로 기능을 추가하기
- 읽기만 하는 파일의 문법을 현대화하기

작업 범위 밖에서 개선할 점을 발견하면, 고치지 말고 기록만 한다:

### 규칙 1: 한 번에 하나씩

각 증분(increment)은 하나의 논리적 변경만 담는다. 개별적으로 판단한 관심사를 섞지 않아야 합니다.

**나쁜 행동**: 하나의 증분에서 새 정책을 추가하고, 환경을 리팩터링하고, 평가 로직까지 수정.
**좋은 행동**: 세 개의 커밋으로 분리 — 변경마다 하나씩.

### 규칙 2: 항상 실행 가능하게 유지

각 증분 이후에도 코드는 실행되고 기존 테스트는 통과해야 한다. 슬라이스 사이에 깨진 상태로 두지 않습니다.

- `pytest`가 통과하는가?
- CVXPY 풀이가 여전히 `prob.status == OPTIMAL`인가?
- Phase 검증(예: `peak_total/CAP ∈ [1.25, 1.35]`)이 여전히 성립하는가?

### 규칙 3: 미완성 기능은 플래그로 감춘다

기능이 아직 준비되지 않았지만 증분을 병합해야 한다면, 설정 플래그로 분기합니다:

```python
# 작업 중인 기능 플래그 (기본 비활성)
ENABLE_BULLWHIP_METRIC = False

if ENABLE_BULLWHIP_METRIC:
  # 아직 검증되지 않은 bullwhip 계산 경로
  ...
```

이렇게 하면 미완성 작업을 노출하지 않고도 작은 증분을 메인에 병합할 수 있습니다.

### 규칙 4: 안전한 기본값

새 코드는 보수적이고 안전한 동작을 기본값으로 하되, 과도한 안전장치로 인해 직관성을 파괴하지 않아야 한다.

```python
def evaluate(policy, options=None):
  options = options or {}
  persist = options.get("persist", False)   # 기본은 저장 안 함
  ...
```

위와 같이 과도한 안전장치를 제외하고, 아래처럼 필요한 사항만 넣는다.

```python
def evaluate(policy, options=None):
  options = options
  ...
```

### 규칙 5: 되돌리기 쉽게

각 증분은 독립적으로 되돌리기 가능해야 한다:

- 추가형 변경(새 파일, 새 함수)은 되돌리기 쉽다 — 선호한다
- 기존 코드 수정은 최소한으로, 초점을 좁혀서
- 하나의 커밋에서 무언가를 삭제하면서 동시에 교체하지 않는다 — 분리한다
- 저장된 결과 형식(`result/runs/`)을 바꿀 때는 이전 결과를 읽는 경로를 함께 남긴다

## Working with Agents

서브 에이전트들에게 점진적으로 구현할 작업을 지시할 때, 각 증분의 범위와 목표를 명확히 하세요. 

예시

```
"계획 중 과제 3을 실행해보자라고 할 때, 

시뮬레이터 구현부터 시작하세요.
벤치마크 구현부터 시작하지 마세요.
```

## 증분 구현 시 체크리스트

- 변경 사항을 통한 새로운 기능이 예상대로 동작하는 지 확인
- 빌드가 성공했는 지 확인
- 꼼수 부린 것이 없는 지 확인

## 위험 신호

- 테스트 없이 500줄 이상의 코드를 작성
- 이걸 추가하면 어떨까?라는 단순 의문성에서 나온 추가 코드
- 증분 구현 간 빌드 또는 테스트 실패 했을 경우
- 일회성 작업을 위해 새로운 유틸리티 파일을 생성했을 경우
- 속도를 높이기 위해 테스트/검증 단계를 건너뛴 경우

## Verification

모든 작업이 끝난 뒤에:

- 각 task가 개별적으로 테스트되고 승인되어야 함
- 전체 빌드가 완료 되어야 함
- 프롬프트 기능 요구사항 대로 정상적으로 작동해야 함
